# CareBridge frontend API contract inventory

## Canonical choices implemented by the current backend

- `GET /patients/me/clinical-records` returns the mounted screen's `ClinicalRecord[]`; the grouped bundle expectation belongs only to an unmounted component.
- Appointment status values are `booked`, `approved`, `rejected`, `completed`, and `cancelled` in both patient and doctor views.
- Prescription downloads return JSON `{ filename, content_type, file_base64 }`, matching the mounted records screen and existing JSON download helper.
- The C++ API implements the choices above. The following additional API routes support the integrated laboratory and monitoring workflows: clinician lab technician listing and lab-order creation/listing; technician assigned-order listing/detail/start/result submission; patient/doctor lab result reads; patient timeline/vitals/alerts reads and alert acknowledgement; lab technician provisioning; and logout.
- Requests use JSON and errors return `{ "detail": string }`. CORS is limited to the configured local frontend origin; API is bound to `127.0.0.1`.

## Scope and evidence rules

This document began as an inventory of operations expressed in `frontend/src`. Its table records frontend expectations; the `Implemented` status below now reflects the C++ replacement server and `backend/tests/api-smoke.ps1`. A TypeScript generic or component property access alone does not prove a response shape. No behavior was copied from the read-only reference backend.

There are **28 distinct method/path operations** in the source. One operation (`POST /patients/me/vitals`) is in `features/timeline/HealthRecords.tsx`, which is not imported by `App.tsx`; it is source code but not currently reachable through the main app. The old unused endpoint constants are listed separately below and are not counted as requests.

Unless stated otherwise, the frontend considers any `response.ok` status successful. A `204` is returned as `undefined`; every other successful `apiRequest` is parsed as JSON. The caller may ignore that return value. The API client does not define endpoint-specific status codes. Therefore endpoint-specific success/error codes are **unknown**; only “2xx accepted by Fetch” is established. A non-2xx response is parsed for a JSON string property `detail`; otherwise the UI shows a generic status message. Network failures surface as fetch errors. No response-schema validation is performed except the `apiDownload` helper's base64/content-type checks.

The base URL is `VITE_API_BASE_URL` or, by default, `http://127.0.0.1:8001`. `apiRequest` sends `Accept: application/json`, sets `Content-Type: application/json` when a body is provided, and conditionally sends `Authorization: Bearer <in-memory token>`. No cookies are configured.

## Authentication and authorization contract visible to frontend

- Patient and doctor registration are separate POST endpoints. Each flow then calls login automatically.
- Login returns an access token response; `authService` stores only `access_token` in module memory and immediately requests `/auth/me`.
- Requests attach `Authorization: Bearer <token>` if a token is present. There is no localStorage/sessionStorage/cookie persistence, token refresh, or server logout request.
- Logout only clears the in-memory token and React user state.
- The frontend uses `/auth/me` `User.role` to show doctor versus patient navigation. It does not enforce access at the HTTP helper layer.
- `admin` is present in the `UserRole` type, but there is no admin screen or role-specific behavior. All non-doctor roles get the patient menu and patient dashboard path.
- Login failures are surfaced from `detail` when it is a string; otherwise the helper reports `Request failed with status N`. Failure of `/auth/me` clears the token.
- Future backend must enforce account state, role, ownership, consent, and per-resource authorization server-side. A UI menu is not an access boundary.

## Endpoint constants not currently called

`services/endpoints.ts` declares `/health`, `/symptoms`, `/patients/me/timeline`, `/patients/me/vitals` (the latter has only the unmounted call above), `/providers`, and `/alerts`. Of these, `/patients/me/vitals` has one source call. The others have no request caller in the current `frontend/src` scan. Do not implement them solely because a constant exists; establish whether the intended UI should use them.

## API errors and unresolved contract details

The UI establishes no endpoint-specific error status map, error schema beyond optional string `detail`, retry policy, pagination, sorting guarantees, or id format. Most callers display server messages directly. There is no 401-driven logout or token refresh. Exact success status codes, registration response bodies, null behavior, ordering, and validation errors remain unknown unless specified in a caller expectation above. Date inputs use local date strings; appointment/follow-up writes use ISO UTC instants; availability returns untyped `HH:mm`-looking strings; demo timestamps sometimes omit offsets. The replacement contract must explicitly settle these formats.
